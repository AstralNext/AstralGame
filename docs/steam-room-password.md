# Steam 房间双层密码（规范草案）

> 状态：草案，**未实现**。
>
> 决策更新（本轮）：
> - Steam 路径**取消短码邀请**，入口只有大厅搜房与 Steam 好友邀请；邀请不再携带任何口令。
> - 「基础密码 = `join_token`」的前提**不再成立**。
> - 基础密码暂定为**全工具统一口令**（全局一个，随安装包分发），额外密码为**每房自设**。
> - **「统一口令」这一层等待用户确认**；未确认前实现不动。
>
> 前置阅读：`docs/steam-room-discovery.md`。

## 1. 目标与威胁模型

| 门 | 谁需要知道 | 挡谁 |
|---|---|---|
| 基础密码（统一口令） | 所有本工具用户 | 从公共列表乱点进来的陌生 Steam 用户、扫房脚本 |
| 额外密码（每房自设） | 房主额外告知的人 | 知道统一口令的熟人、转发房间链接的人 |

攻击者能力假设：能看到 lobby 公开数据与房间名；能从公共列表直接进房；能录制并重放握手；能在线暴力尝试。**不在范围**：拥有 Steam 平台内部权限者、键盘记录器、房主本机被攻陷。

明确说明：统一口令对**所有本工具用户可见**，并会随安装包扩散，因此它只是「低成本门槛」，不是强凭据；真正的房级边界由额外密码承担。

## 2. 两道门分工

| 项 | 基础密码（统一口令） | 额外密码（每房） |
|---|---|---|
| 来源 | 随客户端分发的一份全局口令 | 房主建房时手动设置 |
| 作用域 | 全工具 | 单个房间 |
| 是否进邀请 | 否（Steam 已无邀请载荷） | 否 |
| 是否进 lobby data / 房间名 | 否 | 否 |
| 校验位置 | 握手阶段，房主进程内 | 同一握手阶段 |
| 失败错误码 | 1 | 2 |
| 是否可单独轮换 | **否**，只能整体换版本 | 是，房主随时可改 |
| 默认状态 | 始终启用 | 可选，不设即单密码房 |

「两个都每房一个」被否决：与统一口令职责重复，且增加房主配置成本。

## 3. 密码怎么传

### 3.1 原则

- 不明文出现在 HELLO / AUTH 载荷里；
- 不明文出现在 lobby `name` 或任何 lobby data；
- 不写入邀请、日志、崩溃上报；
- 校验必须发生在 `assign_member` / `CTL_WELCOME` / 创建 wintun 之前。

### 3.2 挑战-响应流程

1. 客人建立 P2P 连接后**不直接发 HELLO**；房主对该连接发 `CTL_CHALLENGE { ver, nonce }`，`nonce` 为 16 字节随机数，**由房主生成**，一次性、5 秒过期。
2. 客人回 `CTL_AUTH { ver, game_id, steam_id, nickname, proof_basic[, proof_extra] }`：
   ```
   proof = HMAC-SHA256(password_hash, DOMAIN || nonce || host_steam_id || client_steam_id || game_id)
   ```
   - `password_hash` = `PBKDF2-HMAC-SHA256(password, salt, 150000)`；
   - 基础与额外各自独立计算 `proof_basic` / `proof_extra`，便于区分错误码。
3. 房主用本地保存的 `salt + hash` 重算并**常量时间比较**。
4. 两项通过才进入 `assign_member` → `CTL_WELCOME` → 建 wintun；任一失败立即回 `CTL_KICK { code }` 并断开。

`nonce` 必须由房主发：客户端自选 `nonce` 时，攻击者可整组重放「nonce + proof」；房主发的一次性 `nonce` 才能阻断重放。

### 3.3 统一口令（基础密码）的代价

- **对所有用户可见**：任何拿到本工具的人都能通过这道门，它只过滤「没有工具、从公共列表乱点」的陌生用户。
- **随安装包扩散**：一旦打包分发就无法回收；口令不能作为敏感凭据，也不应写成可被误认为安全的样子。
- **无法单独轮换**：泄漏后只能整体换版本、强制升级，旧版本会持续可用，需要服务端或版本号配合封禁。
- **不得复用**：不允许把用户个人密码、额外密码、后台密钥当作统一口令。
- 建议实现：口令不硬编码在明文源码里，构建时注入；日志与界面对外只显示「需要统一口令」而从不回显。

### 3.4 额外密码（每房）

- 只在房主内存中保存 `salt + PBKDF2 hash`，重启后需重新输入或重新设置；
- 不写入 lobby data、房间名、日志；
- 通过房外渠道（口头、群聊）告知；
- 要求：至少 6 位、不强制字符类型、上限 64；设置时提示「额外密码只防熟人，不防拥有统一口令者的暴力破解」。

## 4. 时序与连接状态机

```
Connected → Challenged → Authed → Welcome
```

- `Connected` / `Challenged` 阶段的连接**不得**进入 `conns` 转发表、不得分配虚拟 IP、不得出现在 roster、不得转发任何 IP 包或应用 RPC。
- 认证通过前，房主只接受控制层 AUTH 消息，其余帧一律丢弃。
- 与现状衔接：现有 `on_control` 的 `token` 校验已发生在 `assign_member` 之前，改造时保持该顺序，把 token 校验替换为挑战-响应。
- 挑战发出后 5 秒未收到合法 AUTH：回 `KICK code 5` 并断开，**不依赖** 15 秒 `START_TIMEOUT`；客人端立即显示明确失败。

## 5. 错误码与文案

| code | 场景 | 客人端文案 | 可重试 |
|---|---|---|---|
| 1 | 统一口令不匹配（客户端版本过旧或非本工具） | 客户端版本不一致，请更新到最新版本 | 否 |
| 2 | 额外密码错误 | 额外密码不正确 | 是 |
| 3 | 房间已满 | 房间人数已满 | 否 |
| 4 | 协议版本不符 / 不支持双层密码 | 双方版本不一致，请升级到同一版本 | 否 |
| 5 | 认证超时 | 房主未响应认证，请确认网络后重试 | 是 |
| 6 | 房主关闭房间 | 房主已关闭房间 | 否 |

`Kick` 需携带 code；客人端按 code 映射文案，不靠超时兜底，也不用笼统的「加入失败」。

## 6. 隐私

- lobby `name` 只放显示名，lobby data 只放 `ag_gate` 等公开字段；
- 调试日志（含 `ASTRAL_STEAM_DEBUG`）不得打印口令、`proof`、`salt`，只允许 `code` 与 `steam_id`；
- 内存中的明文只在设置密码的瞬间存在，随后立即转 hash。

## 7. 兼容

- `CTL_CHALLENGE` / `CTL_AUTH` 带 `ver`；旧版客户端连新房主：5 秒后 `KICK code 4`；
- 新版客户端连旧房主：收不到 CHALLENGE，超时后提示「房主版本过旧」；
- 不允许静默降级为单密码；降级必须由房主显式设置。

## 9. 测试计划

- Rust 纯函数单测：proof 计算与校验、常量时间比较、nonce 过期、重放拒绝、错误码映射。
- Rust 状态机单测：未认证连接不分配 VIP、不进 roster、不转发数据。
- Dart 单测：错误码 → 文案映射；`Kick` 到达时立即失败而非等待超时。
- 双账号：统一口令错 / 额外密码错 / 超时 / 满员分别得到对应文案。
